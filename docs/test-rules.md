# Правила тестов бэкенда cv-customs (webinar edition)

Единственный источник правил для тестов под `tests/`. На него опираются
скилл `/api-tests` и агент `test-reviewer`; дублировать эти правила
в скиллах и агентах запрещено — расходятся на первой же правке.

У каждого правила есть идентификатор. Ревью ссылается на идентификатор,
а не пересказывает правило своими словами.

Стенд, на котором всё держится, живёт в [`tests/conftest.py`](../tests/conftest.py).
Прежде чем писать тест, прочитай его — половина правил ниже это просто
«не делай руками то, что уже есть в фикстуре».

---

## STRUCT — расположение и именование

| ID | Правило |
|---|---|
| STRUCT-001 | Тесты лежат в корневом `tests/`, **не** рядом с кодом (код — в `backend/src/cv_customs/`). Так настроен `testpaths` в `pyproject.toml`. |
| STRUCT-002 | Раскладка по слою: `tests/api/` — ручки через `TestClient`; `tests/infra/` — S3, health, настройки. |
| STRUCT-003 | Файл — на фичу, а не на роутер: `tests/api/test_<feature>.py`. Новый файл заводится, только если фичи в существующих действительно нет. |
| STRUCT-004 | Имя теста описывает поведение, а не вызов: `test_reset_confirm_rejects_unknown_token`, а не `test_post_confirm_2`. |
| STRUCT-005 | Докстринг модуля объясняет, **что за контракт** проверяется и какие ветки покрыты. Докстринг теста нужен, только когда неочевидна предпосылка. |
| STRUCT-006 | Регрессионный тест на исправленный баг обязателен и называется по багу. |

## FIXT — фикстуры и стенд

| ID | Правило |
|---|---|
| FIXT-001 | Стенд берётся из `tests/conftest.py`. Собственный `create_async_engine`, `async_sessionmaker`, `dependency_overrides` или `noop_lifespan` в тест-файле — **запрещены**. |
| FIXT-002 | Приложение поднимается только через `build_client(...)`. Без аргументов — боевое `cv_customs.main.app`; `build_client(routers=[...])` — одноразовое приложение из указанных роутеров (нужно для ручек за feature-флагом, например MFA). |
| FIXT-003 | Тест-файл добавляет только **сидинг своих данных**. Пользователь заводится через `make_user(...)`, заголовки — через `auth_headers(user_id)`. Собственный `create_access_token` в теле теста не нужен. |
| FIXT-004 | Ресурсы `app.state` (`email`, `s3`) выставляет `build_client` и он же откатывает. Присваивать `app.state.*` руками нельзя: боевое приложение — модульный синглтон, утечка состояния уедет в соседний тест. |
| FIXT-005 | Умолчания стенда — это ветки «внешнего сервиса нет»: `email=None`, `s3=None`. Нужен захват писем — запроси фикстуру `email_client` и передай `build_client(email=email_client)`; нужен блоб-стор — передай свой fake-S3 (`build_client(s3=fake_s3)`, образец в `test_resume_upload.py`). |
| FIXT-006 | Фикстура, которая ничего не убирает за собой, — обычная `return`-фикстура, а не генератор с `yield`. Уборка — забота `build_client` и `db_engine`. |
| FIXT-007 | Зависимость, которой может не быть в неполном окружении прогона (`pyotp`, `httpx`), подключается через `pytest.importorskip`, а не голым `import` в шапке: тест скипается, а не роняет сбор всей сессии. |

## MOCK — границы моков

| ID | Правило |
|---|---|
| MOCK-001 | Мокаются **только внешние границы**: S3 в `infra/storage.py`, почта в `infra/email.py`. |
| MOCK-002 | Репозитории (`db/repositories.py`) и сами хендлеры **не мокаются** — тест ходит в реальную SQLite. Мок репозитория прячет ровно те дефекты (сериализация, констрейнты, миграции), ради которых тест и пишется. |
| MOCK-005 | Подмена — только через `monkeypatch` (или передачу двойника в `build_client`), чтобы откат был автоматическим. |

## AUTH — авторизация

| ID | Правило |
|---|---|
| AUTH-001 | У каждой закрытой ручки минимум три теста: happy path, отказ авторизации, отказ валидации. |
| AUTH-002 | Тест «чужой объект» обязателен для всего, что адресуется по id. Ожидание — **404, а не 403**: существование чужой сущности не раскрывается. Так ведёт себя `/api/v1/resumes/{id}`. |
| AUTH-003 | Невалидный UUID в пути — тоже 404, а не 422: ручки ловят `ValueError` руками (см. `_load_resume` в `api/resumes.py`). |
| AUTH-004 | Токен выпускается через `auth_headers(user_id)`; второй пользователь заводится `make_user("other@example.com")`. |

## DB — база и изоляция

| ID | Правило |
|---|---|
| DB-001 | SQLite-in-memory через `aiosqlite`, схема создаётся из `Base.metadata`. Postgres в тестах не используется, пока тесту не нужна именно постгресовая фича. |
| DB-002 | БД своя на каждый тест (`db_engine` — function-scoped). Тесты не зависят от порядка выполнения и от данных друг друга. |
| DB-003 | Состояние после запроса проверяется через реальную сессию: `async with session_factory() as session: …` + репозиторий или `select(...)`. |

## ASSERT — ассерты

| ID | Правило |
|---|---|
| ASSERT-001 | **Ассерт на суть требования, а не только на статус-код.** Тест, который проверяет 200 и не смотрит в тело, требование не проверяет. |
| ASSERT-002 | В ассерт статуса кладётся тело: `assert resp.status_code == 200, resp.text`. Без этого падение в CI нечитаемо. |
| ASSERT-003 | Проверяются значимые поля ответа, а не факт их наличия: значение `size_bytes`, конкретный `template_alias`, реальный `ip_address` в audit-log. |
| ASSERT-004 | Побочный эффект проверяется у источника: письмо — в `email_client.sent`, запись — в БД, блоб — в fake-S3. «Ручка вернула 202» про побочный эффект не говорит ничего. |
| ASSERT-005 | Негативный кейс обязан быть осмысленным: тест должен падать по **той** причине, которую проверяет. Классическая ловушка — получить 422 на схеме вместо ветки хендлера (см. комментарий в `test_reset_confirm_requires_email`). |
| ASSERT-006 | Ассерт на полный JSON-дамп ответа запрещён: ломается от любого нового поля и ничего не сообщает о требовании. |

## MARK — маркеры

| ID | Правило |
|---|---|
| MARK-004 | Тест, написанный по тест-плану, несёт `@pytest.mark.case("TC-NNN")` — это связь плана из `plans/` с кодом. |

## FORBID — сводка запретов

| ID | Запрещено | Почему |
|---|---|---|
| FORBID-001 | Свой `create_async_engine` / `dependency_overrides` в тест-файле | FIXT-001 |
| FORBID-002 | `time.sleep` и любые ожидания без таймаута | тест виснет в CI |
| FORBID-003 | Обращение в сеть (настоящий Postgres, S3/MinIO, SMTP) | MOCK-001, тесты гоняются офлайн |
| FORBID-004 | Зависимость от порядка тестов и общее состояние между ними | DB-002 |
| FORBID-005 | Тавтология вроде `assert 200 == 200` и тест без единого ассерта | тест не может упасть |
| FORBID-006 | Ассерт на полный JSON-дамп ответа | ASSERT-006 |
| FORBID-007 | Хардкод данных из чужих окружений: настоящие e-mail, ключи, id из прода | утечка и нестабильность |
| FORBID-008 | Секреты и ключи в коде теста | окружение задаёт `tests/conftest.py` |
| FORBID-009 | Дубль теста вместо правки существующего, когда сценарий уже поднят | правится существующий тест — не хватает обычно ассерта, а не сценария |
| FORBID-010 | Правка production-кода «чтобы тест позеленел» без отдельного решения | красный тест — это вопрос «дефект сервиса или неверная предпосылка», а не повод менять хендлер |

## Как проверить себя перед ревью

```bash
uv run pytest -q
uv run python scripts/openapi_snapshot.py --check   # снапшот контракта не отстал
```
