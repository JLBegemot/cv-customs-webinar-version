# Описание PR к написанным тестам

Цель: ревьюер видит, **на какие ручки** написаны тесты и **какие сценарии** они
покрывают — не поднимая переписку с автором и не читая контракт.

Готовится всегда, даже если PR ещё не создан: платформа — GitHub, но `gh`
в системе не установлен, поэтому `/ship` пушит ветку и печатает готовый текст,
а PR создаёт человек по ссылке из вывода `git push` (появится `gh` — этот же
текст идёт в `gh pr create --body`).

---

## Что обязательно содержит

1. **Ручки** — идентификаторы как в контракте: `POST /api/v1/resumes/upload`.
2. **Режим проектирования** — `full` (вся ручка) или `delta` (только изменение).
3. **Ссылка на тест-план** — `plans/<id>-test-plan.md`, он в том же диффе.
4. **Сценарии, которые фактически реализованы** — по строке на тест.
5. **Идентификатор теста** — `tests/api/test_x.py::test_name`. Это то, что ревьюер
   скопирует в `pytest`, чтобы прогнать один тест.

## Только фактически реализованное

В описание попадает то, что есть в диффе, — не тест-план целиком. План по ходу написания
меняется: кейсы объединяются в `parametrize`, разбиваются, отпадают как дубли, добавляются
новые. План, приложенный как есть, начинает врать про содержимое PR.

Отсюда:

- **Кейсы, которые не были написаны, в описание не включать** — ни строкой «не написан»,
  ни счётчиком «N из M кейсов плана». Что не реализовано — сказать пользователю в финальном
  отчёте: это разговор с автором, а не с ревьюером.
- **Сценарий описывать так, как он реализован в коде**, а не как он был сформулирован
  в плане.
- **Идентификатор строки — путь к тесту из кода, а не `TC-NNN` из плана.** Номера кейсов
  к моменту PR уже не совпадают с тестами. Связь план ↔ код держит
  `@pytest.mark.case("TC-NNN")` в коде, и её видно в диффе.
- `⏳`-заготовки (`@pytest.mark.skip`) — это реализованное: они лежат в диффе. Включать
  наравне с рабочими тестами, с пометкой `⏳ заготовка`.

## Доработанные существующие тесты

Правка существующего теста — тоже содержимое PR: в диффе есть изменённая функция,
и ревьюеру нужно понимать, что там появилась новая проверка, а не переформатирование.

Такие тесты идут строкой в той же таблице с пометкой `➕ дополнен`; в колонке «Сценарий» —
**что именно добавлено**, а не весь смысл теста заново.

В итоговой строке считать отдельно: `3 новых + 2 дополненных + 1 заготовка`. Смешивать
доработки с новыми в одном счётчике нельзя — по нему судят об объёме PR.

## Шаблон

````markdown
## Автотесты: <ручка или фича>

| | |
|---|---|
| **Ручки** | `POST /api/v1/resumes/upload`, `GET /api/v1/resumes/{resume_id}/original` |
| **Профиль** | `http` |
| **Режим проектирования** | delta (только изменение) |
| **Тест-план** | `plans/10-resume-download-test-plan.md` |

### Реализованные сценарии

| Сценарий | Тип | Вид | Тест |
|---|---|---|---|
| Скачанный блоб байт-в-байт равен загруженному, `Content-Disposition` с filename | Positive | ✅ новый | `tests/api/test_resume_upload.py::test_download_returns_original_bytes` |
| Скачивание при недоступном S3 — 503, а не 500 | Negative | ✅ новый | `tests/api/test_resume_upload.py::test_download_without_s3_returns_503` |
| Чужое резюме — 404, существование не раскрывается | Negative | ✅ новый | `tests/api/test_resume_upload.py::test_download_cross_user_returns_404` |
| Добавлен ассерт на запись `resume_upload` в audit-log | Positive | ➕ дополнен | `tests/api/test_resume_upload.py::test_upload_pdf_stores_blob_and_metadata` |
| Битый ответ протокола S3 — нет способа воспроизвести подменой | — | ⏳ заготовка | `tests/api/test_resume_upload.py::test_download_s3_protocol_error` |

### Проверки

- `uv run pytest -q` — <N> passed
- `uv run python scripts/openapi_snapshot.py --check` — снапшот совпадает

**Итого:** 3 новых теста + 1 дополненный + 1 заготовка.
````

## Правила оформления

- Ручки — точно как в `docs/openapi.json`, с плейсхолдерами пути.
- Снапшот контракта обновлён (`--dump`) — сказать об этом отдельной строкой: ревьюер
  увидит `docs/openapi.json` в диффе и должен понимать, почему он там.
- Ничего не выдумывать: не было прогона — не писать его результат.
