# API Tests — Playbook

Цель: по ручке или задаче построить структурированный тест-план,
а после согласования — написать тесты.

Транспорт один (REST поверх FastAPI), поэтому ось разбиения здесь не транспорт,
а **профиль ручки** — см. [`profiles.md`](profiles.md). Заголовки шагов ниже
и разделы в `profiles.md` совпадают: читать вместе, а не по очереди.

Правила написания тестов — в [`docs/test-rules.md`](../../../../docs/test-rules.md).
Этот файл про **процесс**, тот — про **код**. Не дублировать.

## Шаг 0 — Определить режим

| Режим | Когда | Скоуп кейсов |
|---|---|---|
| `full` | Ручки нет в репозитории: нет в `docs/openapi.json`, нет тестов | Вся ручка целиком |
| `delta` | Ручка уже есть, задача — покрыть изменение или закрыть пробелы | **Только изменение** |

### Режим определяется по фактам репозитория, а не по формулировке задачи

Формулировка человека — гипотеза, репозиторий — факт. «Новая ручка» регулярно означает
«ручка давно в контракте и покрыта пятнадцатью тестами»: задача переоткрыта, ТЗ скопировано
из старого, автор помнит проект, а не репозиторий.

Поэтому **до** выбора режима проверить две вещи:

```bash
# 1. Есть ли ручка в контракте
jq -r '.paths | keys[]' docs/openapi.json | grep -i '<фрагмент пути>'

# 2. Есть ли тесты на эту ручку
grep -rn '"<путь>' tests/
```

Всё пусто → `full`. Есть хоть что-то → `delta`, и сказать прямо, что найдено:

> Ручка не новая: есть в контракте (`docs/openapi.json`) и покрыта `<N>` тестами
> (`tests/api/test_<feature>.py`). Предлагаю режим `delta` — покрыть изменение.
> Нужен `full` (пересмотр целиком) — скажи, пересоберу план.

Не подгонять режим под формулировку: план на «новую» ручку, которая покрыта, — это
дубли поверх существующих тестов.

### Режим `delta` — что нужно на входе

| Вход | Обязательность | Зачем |
|---|---|---|
| **План в `plans/`** или описание изменения | обязательно | формулы, единицы, границы, out of scope — того, чего нет в контракте |
| **Дифф ветки** (`git diff main...<ветка>`) | обязательно, если ветка есть | имя поля, тип, дефолт, где значение потребляется, где валидируется |
| **Дельта контракта** (`git diff docs/openapi.json`) | обязательно | что реально поменялось в схемах и путях |
| **Описание изменения словами** | если нет ни плана, ни ветки, ни дельты контракта | иначе дельту не определить — остановиться и попросить |

**Ручка на входе может быть не названа.** В `delta` человек часто даёт только задачу
(«покрой то, что в `plans/01-upload-validation.md`»), а список ручек выводится из плана
и диффа. Не требовать имя ручки как предусловие — сначала прочитать источник, потом сказать,
что затронуто, и согласовать скоуп.

### Одно изменение — несколько ручек

Изменение общей Pydantic-схемы, нового поля в разделяемой структуре, общей зависимости
проявляется сразу в нескольких ручках. Все они входят в дельту, даже если в заголовке
задачи названа одна.

В cv-customs типичные источники такого эффекта:

- Pydantic-схема ответа переиспользуется несколькими ручками (`ResumeFileOut`
  отдают и upload, и list, и detail);
- зависимость `get_current_user` меняет поведение всех ручек, где стоит;
- хелпер вроде `_load_resume` (единая точка «404 на чужое и на невалидный UUID»)
  используется несколькими ручками — правка в нём видна во всех.

Что делать:

1. Собрать полный список ручек, где изменение видно — по диффу ветки и по `git diff docs/openapi.json`.
2. Показать список пользователю **до** проектирования кейсов и спросить, берём все или сужаем.
3. В плане группировать кейсы по ручкам, размещение указывать по файлам.

**В режиме `delta` кейсы проектируются только на изменённую часть.** Существующее
поведение не перепроверяется, даже если разбор существующих тестов показал пробелы — такие пробелы
вынести отдельным списком «Дополнительно не покрыто» как информацию, но не включать
в план без явного согласия пользователя.

## Шаг 0б — Прочитать источник требований

Трекера задач в проекте нет; его роль играют `plans/*.md` и дифф ветки.

Из источника вытащить то, чего контракт не содержит:

| Что искать | Пример из этого проекта |
|---|---|
| Формулы расчёта полей | `size_bytes` — фактическая длина блоба, а не заголовок клиента |
| Единицы измерения | `RESUME_UPLOAD_MAX_BYTES` — байты, не мегабайты |
| Границы и лимиты | размер файла, длина `filename` (обрезается до 255) |
| Требования согласованности | метаданные в БД и блоб в S3 создаются вместе или никак |
| Поведение, которого нет в схеме | формат определяется по magic-байтам, а не по `Content-Type` |
| **Out of scope** | «email-верификации нет», «фоновая очистка по ретеншну — вне задачи» |
| Поведение при отсутствии внешнего сервиса | нет S3 → 503 на upload/download, не «тихо без блоба» |

**Out of scope читать так же внимательно, как scope** — он отсекает кейсы, которые иначе
попадут в план ошибочно.

### Приоритет источников

Источники расходятся, и порядок доверия фиксированный:

| # | Источник | Что даёт | Чему верить при конфликте |
|---|---|---|---|
| 1 | **Код хендлера** (`backend/src/cv_customs/api/**`) | как оно работает на самом деле | всегда прав |
| 2 | **Контракт** (`docs/openapi.json`) | что сервис обещает | прав против плана, но не против кода |
| 3 | **Существующие тесты** | что уже считалось верным | не доказательство требования |
| 4 | **Текст плана в `plans/`** | зачем это сделано, out of scope | самое общее |

Каждое расхождение — находка: тест пишется по коду, а расхождение выносится пользователю.

**Контракт генерируется из кода, но отстаёт.** `docs/openapi.json` — снапшот; если
`scripts/openapi_snapshot.py --check` падает, снапшот старее кода, и спроектированные
по нему кейсы врут. Обновить **до** проектирования.

Поэтому в плане у каждого требования помечать источник: `[код]`, `[контракт]`,
`[план]`, `[инференс]`.

## Шаг 0в — Прочитать дифф ветки

Если работа идёт по ветке — прочитать `git diff main...<ветка>`. Это самый информативный
источник: он отвечает на вопросы, которые иначе пришлось бы задавать пользователю.

Что вытаскивать:

| Что | Где искать | Пример |
|---|---|---|
| Точное имя поля | Pydantic-модель в роутере | `size_bytes`, `blob_key` |
| Тип и обязательность | аннотация поля, `Field(...)` | `token: str = Field(min_length=16)` |
| Дефолт | значение по умолчанию в схеме или конфиге | `resume_upload_max_bytes = 5 * 1024 * 1024` |
| Где значение потребляется | хендлер, репозиторий в `db/` | `create_resume_file` |
| Валидация | `field_validator`, ручные проверки в хендлере | sniff MIME по magic-байтам |
| Коды и тексты ошибок | `raise HTTPException(...)` в хендлере | `HTTPException(404, "Resume not found")` |
| Побочные эффекты | запись в БД, блоб в S3, письмо, audit-log | `put_object(blob_key, …)` |

**Коды ошибок берутся из хендлера, а не из контракта.** FastAPI кладёт в OpenAPI только
объявленные `responses`; фактические 400/403/404/409/503 живут в теле функции. Прочитать
хендлер целиком — обязательный шаг, а не опциональный.

Смотреть **строки-контекст** вокруг изменения, а не только добавленные: там видны соседние
поля и иногда чужие баги.

## Шаг 1 — Найти контракт и разобрать ручку

Контракт — `docs/openapi.json`, снапшот `app.openapi()`. Внешнего swagger нет,
контракт = код.

```bash
# схема одной ручки, не читая весь файл
jq '.paths["/api/v1/resumes/upload"]' docs/openapi.json

# схема тела запроса
jq '.components.schemas.ResetConfirmRequest' docs/openapi.json
```

Из контракта извлечь: путь и метод, схему запроса, обязательные поля, схему ответа,
объявленные коды. Чего в контракте нет — искать в коде (Шаг 0в).

**Проверить, что снапшот не отстал:**

```bash
uv run python scripts/openapi_snapshot.py --check
```

Отстал — обновить `--dump` и сказать об этом в отчёте. Иначе спроектированные
кейсы разъедутся с реальностью.

**Ручки за feature-флагом есть в контракте.** Снапшот снимается с `FEATURE_MFA=true`,
поэтому `/api/v1/auth/mfa/*` в нём присутствуют, хотя в боевом приложении по умолчанию
не примонтированы. Тест на такую ручку поднимается через `build_client(routers=[...])`
(FIXT-002).

## Шаг 1а — Дельта контракта (только режим `delta`)

```bash
uv run python scripts/openapi_snapshot.py --dump
git diff docs/openapi.json
```

Дифф показать пользователю таблицей — это и есть определение дельты:

| Изменение | Что стало | Минимум кейсов |
|---|---|---|
| Новое обязательное поле запроса | `consent` | happy path с полем + 422 без поля |
| Новое опциональное поле | `title` | happy path с полем + happy path без него (дефолт) |
| Новое поле ответа | `size_bytes` | ассерт на значение в happy path, не на наличие |
| Новый код ответа | 409 | негативный кейс, воспроизводящий ровно эту ветку |
| Сменился тип поля | `int` → `str` | ассерт на тип и формат в существующем тесте |
| Новая ручка в существующем роутере | — | полный набор по профилю (`profiles.md`) |

Набор операций не изменился, а схемы разъехались — это тоже дельта: `--check` печатает
такой случай отдельной строкой.

## Шаг 1б — Выявить пробелы в семантике

Контракт описывает **структуру**, но не **бизнес-семантику**. Прежде чем проектировать
кейсы, явно разделить, что известно и что нет.

Типичные пробелы в этом проекте:

| Пробел | Где закрывается |
|---|---|
| Фактические коды ошибок | `raise HTTPException` в хендлере |
| Что происходит без S3 / почты | ветки `getattr(request.app.state, …, None)` и `_require_s3` |
| Какие форматы файлов принимаются | `utils/mime.py` — sniff по magic-байтам |
| Допустимые значения enum | Pydantic-схема или `Literal[...]` в коде роутера |

Сначала закрывать пробел самостоятельно по репозиторию, и только потом спрашивать.

### Как искать возможные значения — без догадок о нейминге

Перечисляя допустимые значения поля, причины ошибок, значения enum — **искать по месту
использования поля, а не по угаданному префиксу**. Греп по предполагаемому шаблону имени
вернёт ровно то, что было заложено в шаблон, и создаст ложную уверенность в полноте списка.

```bash
# ❌ шаблон предполагает нейминг — значения с другим префиксом не найдутся
grep -rn '"resume_[a-z_]*"' backend/src/cv_customs/

# ✅ поиск по месту использования — собирает фактические значения `action`
grep -rn 'create_audit_log' backend/src/cv_customs/ tests/
```

**Найденный список всегда описывать как неполный**, если он не объявлен в схеме явно.
Формулировать так:

> В коде и тестах встречаются значения `<поле>`: `<список>`. В контракте перечень
> не объявлен, поэтому могут быть и другие. Знаешь дополнительные — уточни, включу в кейсы.

Инференс помечать инференсом, а не подавать как факт из репозитория.

**Ключевое правило: условие срабатывания не выдумывать.** У кейса на ошибку с неизвестным
триггером есть ровно два законных исхода:

1. Пользователь ответил, чем ошибка триггерится → обычный исполняемый кейс.
2. Ответа нет → кейс **в плане** со статусом `⏳` и пометкой «триггер неизвестен».

Третьего нет. **Выбрасывать такой кейс из плана запрещено** — ни молча, ни разделом
«не включено в план». Объявленная в контракте ошибка, которой нет ни в плане, ни в тестах, —
это дыра, о которой никто не узнает: при следующем прогоне дизайнера она снова окажется
«просто непокрытой».

`⏳` — это и есть способ не включать кейс в автоматизацию, не потеряв его.

### Граница между ⏳ и ✖ — один вопрос

> Сможет ли человек выполнить этот кейс руками, когда появятся данные или выяснится условие?

| Ответ | Статус | Что делает писатель |
|---|---|---|
| Да — не хватает только данных, доступа или знания условия | `⏳` | строка в плане + `@pytest.mark.skip(reason=…)`-заготовка с описанием сценария |
| Нет и не сможет никогда | `✖` | ничего: ни теста, ни заготовки, только строка в плане |

**Недостижимость через чёрный ящик — это ✖, а не ⏳.** Если состояние нельзя поднять
через API или фикстуры, руками его тоже не поднять. Распознавать самостоятельно,
не спрашивая пользователя.

Типичные `✖` в этом проекте:

- поломка внешнего сервиса, которую нельзя воспроизвести подменой границы
  (fake-S3 умеет «упасть на put», но не умеет, например, вернуть битый ответ протокола);
- ветки с `pragma: no cover` (гонка двух одновременных delete одного резюме).

**✖ — не повод убрать кейс из плана.** Он не идёт в код, но остаётся строкой: иначе
дыра исчезает, и следующий прогон откроет её заново.

## Шаг 2 — Найти инфраструктуру вызова

Обвязка вызова — это фикстуры из `tests/conftest.py`. Своей обвязки тест не заводит
(FIXT-001).

| Что нужно | Фикстура |
|---|---|
| Приложение и клиент | `build_client()` / `build_client(routers=[...])` |
| БД и сессии | `db_engine`, `session_factory` |
| Почта с захватом отправленного | `email_client` |
| Блоб-стор | fake-S3 руками в тест-файле + `build_client(s3=…)` (образец в `test_resume_upload.py`) |
| Пользователь | `make_user(email, password=…)` |
| Заголовок авторизации | `auth_headers(user_id)` |

Чего в conftest нет — **зафиксировать в плане как требование к инфраструктуре**
и продолжить, не останавливаться. Требование формулируется по смыслу («нужна фикстура,
поднимающая резюме с версией»), способ выбирает писатель.

Если новая фикстура нужна нескольким файлам — это правка общего `tests/conftest.py`,
а она идёт в гейт Шага 6б: conftest трогают все тесты.

Обвязку файловых ручек (fake-S3) смотреть в [`profiles.md`](profiles.md).

## Шаг 4 — Найти и прочитать существующие тесты

Минимум два поиска — каждый находит то, что не находит другой:

```bash
# 1. по строке пути — тесты, которые дёргают ручку
grep -rn '"/api/v1/resumes' tests/

# 2. по сценарию — тесты, поднимающие нужное состояние, но проверяющие его другим способом
grep -rn 'blob_key\|FakeS3' tests/
```

Для каждого найденного файла **прочитать файл целиком** и понять:

- имена тест-функций и что говорит докстринг модуля;
- что отправляется в запросе (какие поля, какой пользователь);
- что проверяется в ассертах (какие поля ответа, какие значения, какой код);
- есть ли проверки побочных эффектов (БД, письма, блоб в fake-S3).

Это необходимо, чтобы точно понять, что уже проверено: тест с именем
`test_upload_pdf_stores_blob_and_metadata` может проверять только код ответа
без полей тела — сценарий воспроизведён, а суть требования не проверена.

### Поиск по строке пути находит не всё

Поиск 1 находит тесты, которые **зовут вашу ручку**. Он не находит тесты, которые
уже поднимают нужное состояние системы, но проверяют его другим способом — например,
проверяют блоб в fake-S3 после upload'а, не дёргая download-ручку.

Нашёлся тест, который поднимает сценарий, — это **правка существующего теста**, а не новый
тест.

В режиме `delta` дополнительно проверить: не покрывает ли какой-то существующий тест
изменённое поле уже сейчас. Такое бывает, если тест писали с запасом или поле было
опциональным до изменения.

Найдя тесты, зафиксировать для отчёта: сколько их и в каких файлах. Это доказательство,
что режим `delta` выбран правильно (Шаг 0).

## Шаг 5 — Определить пробелы

Для каждого сценария из требований — два вопроса, оба обязательны:

1. **Сценарий** — воспроизводит ли какой-нибудь тест это состояние системы и этот запрос?
2. **Ассерт** — проверяет ли он ровно то, из-за чего сценарий существует?

«Нет» на любой из вопросов — пробел, кейс идёт в план. Тест может честно поднять всё
нужное состояние и не проверить главного — тогда сценарий воспроизведён, а требование нет.

**Для ядра изменения проверка обязательна.** По каждому требованию задать прямой вопрос:
есть ли хотя бы один ассерт **на значение**, который упадёт, если это требование сломать?
Нет — кейс идёт в план, даже если сценарий формально «уже проверен». Формула, единица
измерения, порядок статусов, форма пустого ответа без ассерта на значение не проверены
вообще.

Чем крупнее ответ ручки, тем чаще проваливается именно второй уровень: у ответа
из двадцати полей тест обычно проверяет два.

Отсюда следствие для Шага 8: если сценарий воспроизведён, а не хватает проверки — это
**правка существующего теста**, а не новый тест.

## Шаг 6 — Спроектировать тест-кейсы

Включать только пробелы из Шага 5 — сценарии без теста или без ассерта на суть.
Обязательные категории кейсов на профиль — в [`profiles.md`](profiles.md); ниже то,
что действует всегда.

### Параметризация

Предлагать `@pytest.mark.parametrize` в двух ситуациях:

1. **Один сценарий, много входных значений с одинаковым результатом**: несколько невалидных
   значений одного поля, несколько форматов, несколько недопустимых auth-состояний.
2. **Один сценарий, перебор допустимых значений enum или диапазона.**

В плане обозначать: `TC-NNN — <название> [@parametrize: значения]`.

Параметризовать можно, только когда логика теста одинакова для всех параметров. Разные
параметры требуют разного setup или разных ассертов — оставить отдельными тестами.

### Дефолт окружения — не требование

Поле может иметь стабильное значение просто потому, что таким его создаёт фикстура
или дефолт схемы. Это не требование к ручке, и ассерт на такое значение проверяет чужой
дефолт, а не контракт.

Признак: значение задаёт не проектируемая ручка, а `make_user`, дефолт Pydantic-поля,
конфиг. Для таких полей писать проверку **типа, формата и диапазона**, а не значения:

```
❌ TC-NNN — created_at == "2026-01-01T00:00:00+00:00"
✅ TC-NNN — created_at: ISO-8601 с таймзоной
```

Пометка `❓` тут не помогает: `❓` означает «значение выяснится прогоном», а здесь оно
и после прогона останется чужим дефолтом, который поменяется без изменения ручки.

Обратный случай тоже бывает: значение выглядит дефолтом, но задаётся самим тестом
(имя загружаемого файла, e-mail пользователя) — такое пинуется точно.

### Поля, меняющиеся по ходу флоу

Отделять поля, инвариантные по всему флоу, от меняющихся: `updated_at`,
счётчик `total` в списке резюме. Меняющееся поле в общем валидаторе — гонка, а не проверка.
Точное значение пинуется только в проверке той стадии, где оно определено.

### Проверка на дублирование (обязательный проход)

Каждый кейс обязан содержать проверку, которой нет ни в одном другом кейсе плана.
Пройти по списку и для каждого ответить: **что конкретно упадёт в этом тесте и не упадёт
ни в одном другом?** Нет внятного ответа — удалить кейс.

Типичная ошибка: отдельный кейс «структура ответа корректна» / «все обязательные поля
присутствуют» при наличии happy-path кейса, который уже проверяет те же поля.

### Второй проход дедупа: кейсы, проверяемые из одного ответа

Второй вопрос к списку: **какие кейсы проверяются из одного и того же ответа одного
запроса?** Такие обязаны быть одним кейсом — они всё равно лягут в один блок проверок,
и писателю придётся их слить.

Признаки: один и тот же запрос с одинаковым предусловием, различаются только проверяемые
поля ответа; или «поле есть у X» и «поля нет у Y», где X и Y приходят в одном ответе.

```
❌ два кейса, которые сольются в один тест:
TC-002 — ответ содержит непустой id
TC-003 — ответ содержит size_bytes

✅ один кейс:
TC-002 — 201 с телом ResumeFileOut: id — валидный UUID, size_bytes == длине отправленного файла
```

Эти слияния делаются в плане, а не оставляются писателю.

### Формат тест-кейса

```
TC-NNN — <короткое название>
Тип: Positive / Negative
Профиль: http
Сценарий: <что делается>
Предусловие: <состояние — пользователь, резюме, версия, состояние задания>
Запрос: <метод, путь, ключевые поля>
Ожидаемый результат: <код + проверяемые поля ответа и побочные эффекты>
Приоритет: blocker / critical / normal
Источник: [код] / [контракт] / [план] / [инференс]
```

## Шаг 6б — Гейт: все решения пользователя одним блоком

Набросав кейсы, собрать **все** вопросы к пользователю. Это блокирующий гейт: пока
ответов нет, финальная таблица кейсов не выводится.

Что попадает в гейт:

| Класс решения | Примеры в этом проекте |
|---|---|
| **Нетривиальные тестовые данные** | резюме определённой формы (строка в БД без блоба в fake-S3); данные, которых `make_user` не создаёт |
| **Значения, которых дизайнер не знает** | допустимые значения поля, которых нет ни в схеме, ни в тестах |
| **Правка общего `tests/conftest.py`** | новая фикстура в общем стенде — ею пользуются все тесты |
| **Расширение скоупа** | изменение задело несколько ручек: берём все или сужаем |
| **Граница мока** | что считаем внешней границей в спорном случае (новый адаптер в `infra/` — мокать или гонять вживую?) |
| **Выбор между двумя предусловиями** | оба рабочие, но у одного есть цена (время прогона, нестабильность) |

**Сначала проверить репозиторий, потом спрашивать.** Вопрос задаётся только о том,
что нельзя выяснить самому. Порядок «спросил → пошёл проверять → нашёл риск → задал второй
вопрос» запрещён: он превращает один гейт в два круга. Если ответ пользователя открыл новый
риск — назвать риск, предложить решение и **по умолчанию взять детерминированный вариант**,
оставив возможность переопределить.

**Не своё решение в гейт не тащить.** Как назвать тест, в какой файл положить хелпер,
каким способом собрать фикстуру — зона писателя и `docs/test-rules.md`, а не пользователя.
В плане фиксируется требование, способ выбирает писатель.

**Дописывать вопросы после готового плана запрещено** — это перекладывает на пользователя
проверку, что план вообще реализуем. У готового плана открытых вопросов не остаётся:
всё, что требовало решения, разрешено здесь; всё, что решается по правилам, решено
самостоятельно; всё, что нерешаемо, — это `⏳` или `✖` со своей строкой в плане.

Формат блока:

> Перед финализацией плана нужно решить:
>
> 1. TC-004 требует резюме, у которого есть строка в БД, но нет блоба в S3.
>    Сеять строку напрямую в БД или удалять блоб из fake-S3 после upload?
> 2. TC-007 требует новой общей фикстуры `seeded_resume` в `tests/conftest.py` —
>    её увидят все тесты. Заводим общей или локальной для файла?
> 3. Изменение задело и upload, и download. Покрываем обе ручки или только upload?

Не придумывать способ создания данных самостоятельно. Если пользователь говорит,
что сценарий воспроизвести нельзя — кейс идёт в план со статусом ⏳:

```
TC-NNN — <название> [⏳ заблокирован]
Причина: нет способа создать <состояние> в тестовом окружении.
Что нужно: <что конкретно нужно решить для разблокировки>.
```

## Шаг 7 — Определить, где размещать тесты

- **Файл есть** — новые тесты добавляются функциями в существующий файл
  (`tests/api/test_<feature>.py`).
- **Файла нет** — создать новый по STRUCT-003.
- **Тест-логика принципиально другая** (другой стенд) — новый файл рядом.
- **Кейсов много** — разделить: один файл не должен превышать ~700 строк. Разбивать
  по логической группе (позитивные / валидация / авторизация), а не по алфавиту.

Слой определяется тем, что тест дёргает: ручка через `TestClient` → `tests/api/`,
инфраструктура (настройки, health, S3-клиент) → `tests/infra/` (STRUCT-002).

## Шаг 8 — Сформировать итоговый тест-план

План выводится **таблицами** — так его читают и правят, а не абзацами на каждый кейс.
Файл: `plans/<id>-test-plan.md`.

```
## Тест-план: <ручка или фича>

**Режим:** full / delta · **Профиль:** http
· **Источник:** `plans/NN-…md` / ветка `<name>` · **Контракт:** `docs/openapi.json`

### Дельта контракта            ← только delta, таблица из Шага 1а
### Затронутые ручки            ← если изменение задело несколько

### Новые тесты

| TC | Сценарий | Тип | Данные и запрос | Ожидаемый результат | Приоритет | Источник |
|---|---|---|---|---|---|---|

### Правки существующих тестов

| TC | Тест | Что добавить | Тип | Приоритет |
|---|---|---|---|---|

### Кейсы со статусом ⏳ — заготовки

| TC | Сценарий | Причина блокировки | Что нужно для разблокировки |
|---|---|---|---|

### Кейсы со статусом ✖ — в код не идут

| TC | Сценарий | Почему не пройдёт никто | Чем покрыто |
|---|---|---|---|

### Размещение

| Куда | Что |
|---|---|
| Новый файл `tests/api/test_<feature>.py` | TC-001…TC-004 |
| `tests/api/test_resume_upload.py` | TC-008…TC-010 функциями |

### Инфраструктура

| Что нужно | Есть? | Где |
|---|---|---|
| фикстура `<name>` | нет | добавить в `tests/conftest.py` — согласовано в гейте |
```

**Секции «Открытые вопросы» в плане нет.** Вопросы задаются на Шаге 6б до таблицы кейсов;
план — это результат после ответов. Осталась неизвестность, которую пользователь не закрыл, —
она выражается статусом кейса (`❓` / `⏳` / `✖`) и живёт в своей секции.

Приоритет по кейсу обязателен: `blocker` / `critical` / `normal`. Источник требования
помечать: `[код]`, `[контракт]`, `[план]`, `[инференс]`.

Все `❓`-кейсы собрать отдельным списком, чтобы после первого прогона было понятно,
что перепроверить.

### Второй артефакт: `cases.yaml`

Рядом с планом пишется `.claude/tmp/<id>/cases.yaml` — исполняемое подмножество
(только то, что идёт в код). Это то, что уходит в промпт `test-writer` **путями,
а не текстом**.

```yaml
task: 10-resume-download
plan: plans/10-resume-download-test-plan.md
spec: docs/openapi.json
cases:
  - id: TC-001
    endpoint: GET /api/v1/resumes/{resume_id}/original
    profile: http
    action: new                      # new | edit
    target_file: tests/api/test_resume_upload.py
    title: скачанный блоб байт-в-байт равен загруженному
    precondition: авторизованный пользователь, загруженный PDF в fake-S3
    expect: 200, тело == исходные байты, Content-Disposition с filename
    priority: blocker                # blocker | critical | normal
    source: код                      # код | контракт | план | инференс
  - id: TC-007
    endpoint: POST /api/v1/resumes/upload
    profile: http
    action: edit
    target_file: tests/api/test_resume_upload.py
    existing_test: test_upload_pdf_stores_blob_and_metadata
    title: не хватает ассерта на audit-log запись
    expect: строка resume_upload в audit_log с ip клиента
    priority: critical
    source: код
```

Проверить: `uv run python scripts/validate_cases.py .claude/tmp/<id>/cases.yaml`.

`⏳`- и `✖`-кейсы в `cases.yaml` **не попадают** — они живут только в плане.

### Секция «Правки существующих тестов»

Отдельный вид результата, наравне с новыми кейсами. Сюда идёт всё, что нашлось
на Шаге 5: сценарий уже воспроизведён, не хватает проверки или шага.

**Если сценарий воспроизведён — правим существующий тест, новый не пишем** (FORBID-009).
Второй тест с тем же setup ради одного ассерта — дубль: он удваивает время прогона
и создаёт два места, которые придётся править при любом изменении флоу.

Формулировать так, чтобы писатель не перечитывал весь файл: имя теста, что именно добавить,
и одной фразой — почему этого не хватает:

```
| TC-006 | `test_resume_upload.py::test_upload_pdf_stores_blob_and_metadata`
| ассерт на запись в audit_log рядом с проверкой блоба — сейчас проверяются
  только метаданные ответа, а побочный эффект логирования не проверен | Positive | critical |
```

## Незыблемые правила

- **Без утверждённого плана код не пишется.** Гейт Шага 6б не пропускается.
- **Правила написания тестов — только из `docs/test-rules.md`.** Здесь процесс,
  там код; дублировать запрещено.
- **Режим определяется по фактам репозитория, не по формулировке задачи.**
- **Контракт = код.** `docs/openapi.json` — снапшот; проверить
  `scripts/openapi_snapshot.py --check` до проектирования, иначе спроектированные кейсы врут.
- **Коды ошибок брать из хендлера**, а не из объявленных `responses` контракта.
- **Приоритет источников: код хендлера → контракт → существующие тесты → текст плана.**
- **Пробел меряется и сценарием, и ассертом.** Сценарий воспроизведён, но нет ассерта
  на суть требования — кейс идёт в план.
- **Поиск тестов по строке пути находит не всё** — искать ещё по сценарию.
- **Сценарий воспроизведён, не хватает проверки → правка существующего теста**, отдельной
  секцией плана.
- **Кейсы, проверяемые из одного ответа, — один кейс.** Второй проход дедупа обязателен.
- **Дефолт окружения — не требование**: проверять тип, формат и диапазон, а не значение.
- **Поля, меняющиеся по ходу флоу, не пинуются в общей проверке** — гонка, а не проверка.
- Уже проверенные сценарии в список новых кейсов не включать.
- В режиме `delta` проектировать кейсы только на изменение. Пробелы в существующем
  поведении показывать информационно, в план не включать без согласия.
- Нужной фикстуры нет — зафиксировать требование в плане и продолжить, не останавливаться.
- Значения искать по месту использования, не по угаданному префиксу. Найденный список
  объявлять неполным. Инференс помечать инференсом.
- Каждый кейс обязан падать на чём-то, на чём не падает ни один другой кейс плана.
- Кейс на ошибку с неизвестным триггером **включается в план со статусом ⏳**. Выбрасывать
  запрещено. Условие не придумывать.
- **Граница ⏳ / ✖ — один вопрос: пройдёт ли кейс человек руками.** Недостижимое через
  чёрный ящик — ✖, распознавать самостоятельно.
- **✖-кейс всё равно остаётся строкой в плане.**
- **Все решения пользователя — одним блоком в гейте, до таблицы кейсов.** Сначала проверить
  репозиторий, потом спрашивать; дописывать вопросы к готовому плану запрещено.
- Сценарий воспроизводим, но ожидание неизвестно → писать с вероятным значением и пометкой
  `❓`, а не блокировать. `⏳` только для невоспроизводимых сценариев.
